# Agent 调查规则 — 下结论前的证据自检

> **Status**: 🚨 Canonical · Pinned via PUSH hook.
> **Scope**: 任何 AI agent 在用数据下结论时。不是 kg-hub 内部架构。
> **核心**: 用分布下结论前，先验证**这个分布的采集通道当前是否健康**。

---

## 规则 1：看 MAX，不要看 COUNT

判断"某个来源是否还活着"，**用最后活跃时间，不用总量**。

```sql
-- ❌ 错：COUNT 看不出停摆
SELECT platform_source, COUNT(*) FROM sdk_sessions GROUP BY platform_source;
--   codex: 37   ← 这个数字毫无异常感

-- ✅ 对：MAX 一眼暴露
SELECT platform_source, COUNT(*) AS n,
       datetime(MAX(started_at_epoch)/1000,'unixepoch','localtime') AS last_seen
FROM sdk_sessions GROUP BY platform_source ORDER BY MAX(started_at_epoch) DESC;
--   claude  390  2026-08-20 15:37   ← 今天
--   cursor   47  2026-08-17 17:01   ← 3 天前，正常
--   codex    37  2026-07-13 07:22   ← 🚨 5 周前，停摆
```

`COUNT` 是累积量，坏掉后**不会减少**，所以永远"看起来正常"。`MAX` 是新鲜度，**坏掉当天就暴露**。

## 规则 2：分布 ≠ 真相（幸存者偏差）

**"最近 400 条观察全是 claude" ≠ "只有 claude 在干活"。**

因为采集通道坏掉的来源会**直接从统计里消失**——它不是"占比低"，而是"根本不出现"。看到的分布只反映"被观测到的部分"，不反映真实活动。

下结论前问一句：**这个来源如果采集坏了，我看到的数据会是什么样？**
如果答案是"和现在一模一样"，那这份数据不能用来证明任何事。

## 规则 3：分层验证，不要只验一层

一条链路有多个环节，**只验最后一环会漏掉中间的部分失效**。

以 claude-mem 采集为例，至少两层：

| 层 | 验什么 | 只验这层会漏掉 |
|---|---|---|
| `sdk_sessions` | 会话建立了吗 | session 建了但**观察生成失败**（LLM 报错 / 模型名不对） |
| `observations` | 观察真的产出了吗 | — |

两层都要看 MAX。只有 session 没有 observation = hook 部分工作。

## 规则 4：区分"记错了"和"没记"

这两种失效的**影响完全不同**，处置也不同：

| | 记错（标签错误） | 没记（数据缺失） |
|---|---|---|
| 数据 | 存在但归属错 | 根本不存在 |
| 后果 | **污染**下游（误归属、错误聚合） | **黑洞**（覆盖为零，但不污染） |
| 处置 | 要清洗历史数据 | 只要恢复采集，历史无法补 |

判断方法：查目标来源的记录**是否存在**（不是"是否正确"）。
- 零记录 → 是"没记"
- 有记录但字段可疑 → 才是"记错"

## 规则 5：配置在 + 数据断 = 静默失效

这个组合是**判断静默失效的标准切口**：

```
配置缺失  →  数据断    = 正常（没配当然没有）
配置存在  →  数据通    = 正常
配置存在  →  数据断    = 🚨 静默失效，去查执行层
```

静默失效的常见成因：
- **安全门禁**（hash/签名校验不匹配 → 拒绝执行且不报错，如 Codex 的 `trusted_hash`）
- **路径漂移**（配置指向的文件/版本目录已不存在）
- **权限降级**（进程环境变了，如 launchd 不继承登录 shell 的 PATH）
- **契约变更**（上游升级改了接口/事件名，旧配置语法上有效但语义失配）

不要因为"配置看起来没问题"就排除该组件——**配置正确恰恰是静默失效的特征**。

## 实战案例（2026-08-20）

**现象**：codex 会话采集停摆 5 周（07-13 → 08-20）无人察觉。

**踩过的坑**（规则 2 的反面教材）：
> 看到"最近 400 条全是 claude"，推断"只有 claude 在干活" → 错。codex 的活根本没进采集。

**正确的诊断路径**：
1. 规则 1 → `MAX(started_at)` 立刻暴露 codex 停在 07-13
2. 规则 4 → 查到 codex **零记录**（不是标签错），确认是黑洞不是污染
3. 规则 5 → `~/.codex/config.toml` 里 hook 配置全在，但数据断 → 查执行层
4. 根因 → claude-mem 升级把 hook 从 7 个合并成 5 个，`trusted_hash` 全部失配，Codex 静默拒绝执行
5. 规则 3 → 修复后 sessions 层和 observations 层**都验**，确认不是只建 session 空转

**修复成本**：GUI 点几下 Approve，零代码改动。**发现成本**：5 周。

完整排查记录见 cookbook：
`claude-mem-integration-cookbook/docs/TROUBLESHOOTING.md` 第 15 条。

## 附：判据陷阱

**不要用"数量"当判据，要用"内容/时间"**。

同一案例里的反面教材：判断 hook 是否重新 approve 过，用了 `grep -c trusted_hash`（数条数）。
实际上 approve 后 Codex **只更新匹配的 hash，不清理已消失 hook 的旧条目** —— 修复前后**都是 7 条**，数量判据完全失效。

正确判据永远是**最终效果**（数据有没有恢复），不是中间状态的计数。
