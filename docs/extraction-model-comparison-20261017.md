## 0. 结论

1. **Claude 会话自抽取在「纪律」上全面优于网关旧模型**：三个模型边名合规率都是 100%（存量 31–60%）、无类型实体 0（存量 7–17%）、
   重复三元组 0（存量 3–7%）、自创边名 8–13 种（存量每月 1.2k–15.7k 种）。这是 schema 可检索性的决定因素，旧存量里 1.57 万种
   自创边名让 `kg_search` 的边检索基本失效。
2. **但 Claude 抽得稀**：fable 每条 5.6 实体 / 4.3 边、摘要 166 字，deepseek 存量是 12.4 / 12.7 / 398 字。密度差距一部分是规则
   有意为之（回顾/复述类观测只抽新增事实、授权类给空，第 3 轮 23% 的观测属此类），一部分是模型保守。存量的高密度里相当一部分
   是噪声（自创边名、重复三元组、commit 哈希与绝对路径当实体）。
3. **三轮里 fable 这一轮入图质量最好**（边/条 4.27、误并率 0.15、入库误并 1 对），**但可单独归因于模型的只有关系密度与复述判别**；
   误并从 0.76 → 0.35 → 0.15 主要来自服务端消解收紧、类型守卫、dry-run 预览这三项与模型无关的改动。
4. **最划算的方式不是继续换模型**：用同一套 v3 工具链（消解收紧 + 类型守卫 + dry-run + 前瞻 + 已用名）跑 opus，第 2 轮 17 对误并里
   15 对会在新消解下直接消失，成本低于 fable；haiku 的关系稀疏（22% 观测不足 3 边）和类型错配是模型侧问题，不建议做主力。
   比换模型更省的是源头：第 3 轮 23% 是同一会话对同一文件的再读/复述观测，在 claude-mem 侧或取批阶段折叠能省更多。
5. 实际消化：三轮共入库 1,528 条（haiku 500、opus 517、fable 511）+ 33 条判空；live 待处理从 14,106 降到约 12,500。
6. **10-18 补充：给网关路径加上同样的硬约束（入图后归一 + 自定义抽取指令 + max_tokens 8192）后，deepseek 的 50 条验证
   在纪律指标上追平 Claude（合规 100%、无类型 0、脏命名 0），密度 8.7 实体 / 6.7 边、摘要 298 字高于 Claude 三轮；
   模型层归一前合规约 95%。** 这证明「固化逻辑、降低对模型能力的依赖」可行：纪律由链路保证，模型只决定密度与推理。
   遗留：零边 20%（指令收窄后复测不变；账本证实是模型单次返回 `edges: []`、无重试，见 §4.2）、1 次并行读集冲突。
   **已解决**：单次抽取模式（§4.3）零边 0%，调用 7 次降到 1 次。

## 2. 每轮复盘与实践过的优化

### 第 1 轮 · claude-haiku-5-5 · 500 条（b0002–b0026）· 规则 agent-v1

- 结果：500/500 ok；图口径边名合规 100%、边名 10 种、重复 0、零边 0、摘要均长 33.6 字。
- 最差三类：实体误并（跨类型：Issue 并进 Config、Tool 并进 Issue；同名不同路径文件互并）；关系覆盖不足（22% 观测不足 3 边，
  把「3–10」当成了上限）；被后续观测推翻的判断与同一对象的矛盾状态原样入库。
- **教训 → 第 2 轮调参**（检查点登记）：`prompt_version` v1→v2（关系下限 3、可区分命名、被推翻判断不入库、读全文、自检悬空边）；
  `type_guard_on_resolution`=true（服务端，向量候选必须带抽出的类型标签）；`batch_size`=20 不变。
- 顺带修掉的工具问题：复盘工具跨事件循环关驱动（checkpoint 连续失败、gate 偶发 rc=1）；边数查询扫全边超时；retro 参数透传；
  执行器按 refinery 水位选观测（首次冒烟取到了 6 月存量）。

### 第 2 轮 · claude-opus-5-5 · 540 条（b0027–b0053）· 规则 agent-v2 + 类型守卫

- 结果：517 ok / 23 empty；图口径边名合规 100%、13 种、重复 0、摘要均长 75 字。
- **改善证据**：关系不足 3 条的观测 109/500 → 0/517（规则 9）；纯授权/回顾观测给空 0 → 23（规则 9）；跨类型误并 0 例
  （类型守卫，可单独归因）；reuse_mismatch 每条 0.76 → 0.35；同批内被推翻的判断只抽结论（规则 11）。
- 最差三类：同类型近名误并 17 对（兄弟概念共享长前缀、只差一个字符/数字/日期、跨仓库同名文件、描述性名字被泛名吸进；
  首次并错后同名持续命中错误节点）；跨批被推翻的判断 5 组（流式取批看不到后面的更正）；回顾/复述类观测被硬凑出近义节点。
- **教训 → 第 3 轮调参**（`digest_retro tune` 登记）：`resolution_strictness`=v3（服务端：代码类名字与 File/Config 只认完全相等，
  例外为全路径与子路径；只在数字上不同的不复用；包含占比 0.5→0.8；difflib 0.72→0.85）；`submit_dry_run`=true（接口 `dry_run`
  只消解不写图，执行者写入前预览并改名）；`prompt_version` v2→v3（区分词放最前、只差动词的标识符取一个、跨仓库文件写 `仓库:路径`、
  事件带描述、回顾/复述类观测给空或只抽新增、用前瞻与 dry-run、复用已用名）；执行器加 `lookahead` 与 `names-<model>.tsv`。

### 第 3 轮 · claude-fable-5-1 · 520 条（b0054–b0079）· 规则 agent-v3 + 消解收紧 + dry-run

目标是看零边率能否回落到 5% 以下。断路器合上 32 分钟、满 50 条自动断开。

| 项 | 第二批 | 第一批（§4.1） |
|---|---|---|
| 终态 | 50 ok / 1 error / 5 breaker_open（断开瞬间在飞，会重试） | 52 ok / 1 error / 6 |
| 每条 wall | 中位 182 s、p90 327 s | 中位 132 s、p90 251 s |
| 实体/条、边/条（图口径） | 9.34 / 7.14 | 8.67 / 6.73 |
| 归一动作 | 边改名 16（schema 外 11）、补类型 3、脏命名删 1 / 标 7、摘边 5 | 改名 17、补类型 16、删 1 / 标 4 |
| 零实体 | 3 | — |
| **零边 episode** | **10/50（20%）** | 11/52（21%） |

**零边率没有回落，而且不是漏抽实体**：零边样本里 obs-47118 抽出 15 个实体、obs-46197 14 个、obs-24877 13 个、obs-42386 8 个，
实体阶段都正常。查 `model-attempts.sqlite3` 的 `edge_phase` 记录（按 `source_description` 前缀索引取，四条样本全部一致）：

- `ExtractedEdges` 工具调用返回 `{"edges": []}`，`stop_reason=tool_use`，输出 17–23 token，输入 7k–32k token；
- 服务端拿到空列表就结束，**没有第二次询问**——容器里的 graphiti 0.29 `extract_edges` 是单次调用，没有 reflexion 循环（源码里无 `MAX_REFLEXION_ITERATIONS`），
  kg-hub 的 `SingleAttemptAnthropicClient` 也只对 Pydantic 校验失败触发「拒绝结果→下次重试重问」，空列表是合法结果，不触发；
- 自定义指令确实进了边提示（`extract_edges.py:142` 注入 `custom_extraction_instructions`），所以第 5 条收窄与否对这批没有影响。

两批合计：`ExtractedEdges` 调用 111 次，返回空列表 16 次（14%），对应 16 条 episode（obs-46197 两批都空）；零边 episode 里另有 1–2 条是边全部被名字校验/脏命名摘除。
结论：**零边是 deepseek-v4-flash 在这条提示下约 1/6 的概率直接放弃抽边，是模型行为，不是指令或服务端丢弃**；靠改提示词措辞无法稳定压到 5% 以下。

可行的修复（未实施）：在 `graphiti_client.SingleAttemptAnthropicClient.generate_response` 里对 `prompt_name='extract_edges.edge'` 加一条确定性守卫——
ENTITIES ≥ 4 而返回 `edges: []` 时，追加一句「上一次返回为空，本条有 N 个实体，请抽出它们之间的关系」再问一次，仍为空才接受。
只在空结果时多付一次调用（本批约 1/6 的 episode），预期零边率降到与 Claude 自抽取同档（≤ 2%）。这是「硬约束兜底弱模型」思路（docs/GATEWAY-EXTRACTION-OPTIMIZATION.md）在边阶段的延伸。

## 4.3 网关单次抽取模式的 50 条验证（2026-10-19 01:31–01:36 UTC，kg-hub-server:981aa43）

§4.2 证实零边是 graphiti 多阶段结构的问题：抽边那一次调用单独放弃就整条无边。所以不再给它打补丁，而是换链路：
`KG_HUB_INGEST_MODE=single_pass`（PR #190、#195）用会话自抽取的提示词 agent-v3，经同一业务键 `kg_hub.entity_extract`
**一次**调 deepseek 同时拿实体与关系，结果走 `utils/extracted_ingest` 的消解与写图，来源标记 `extraction_mode='gateway_single'`。

先踩了一个坑：#190 首版用强制工具调用取结果，10-19 凌晨首批 11 条全部只有实体、没有边。账本证实 deepseek 在工具调用下
11 次都不写 `edges` 键（当时 schema 里 edges 非必填），唯一写了的一次，边的 JSON 从工具入参溢出成了文本块。
#195 改成不挂工具、模型直接输出 JSON 文本由服务端解析，`edges` 改必填，缺键按形状错误拒收。下面是 #195 上线后的批次。

原因：线上嵌入模型是只认英文的 `BAAI/bge-small-en-v1.5`。graphiti 的提示词是英文，deepseek 在那条链路里写英文长句事实；

修法（由近及远）：
- **提示词旋钮（小改）**：单次调用补充约定里要求 fact 用与观测正文相同的语言写成完整句，含两端实体名与关键细节，长度 60–200 字符；摘要放宽到 1–3 句。改完再跑 50 条，用本节口径复测，目标命中@10 不低于 graphiti 组。
- **嵌入模型（大改）**：换多语言模型（如 384 维的 multilingual-e5-small，维度不变），需要全图重嵌入，另立任务。
